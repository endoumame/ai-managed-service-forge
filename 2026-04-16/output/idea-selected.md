## 選定結果: アイデア4 — DepShield（依存パッケージ脆弱性トリアージ＆修復PRサービス）

## 選定理由

### 1. コモディティ性が最高レベル（5/5）
依存パッケージの脆弱性管理は、あらゆるソフトウェア開発組織が実施すべき業務だが、競争優位の源泉にはなり得ない。Dependabot のアラート地獄は業界共通の課題であり、「やらなければならないが、やりたくない」業務の典型例。

### 2. ハーネスの価値が最も明確に示せる（5/5）
- ドリフト問題への対策が本質 — AI が「影響なし」と判定したものの実は脆弱性が到達可能だった、というケースをハーネスの外部バリデーション（テスト実行、到達可能性の決定論的分析）で防ぐ
- 終了条件の外部管理 —「全 Critical/High にトリアージ結果付与済み」「生成 PR のテスト全パス」を AI の自己申告ではなくハーネスがチェック
- 品質チェック機構 — PR の diff サイズ制限、テストカバレッジ低下検知など

### 3. 自己改善ループが自然（5/5）
- PR 承認/却下の結果が明確なフィードバックシグナルになる
- 「影響なし判定→実際のインシデント発生」の追跡が可能
- パッケージ信頼性スコアの蓄積がサービス全体の価値向上に直結

### 4. プロトタイプの実現可能性が最高（5/5）
- package.json/lockfile のパースは決定論的コードで実装可能
- CVE データとの照合はモックデータで代替可能
- AI によるトリアージ判定は Claude API で実現可能
- Git 操作による PR 生成はプロトタイプレベルで十分デモ可能

### 5. 市場規模（5/5）
- ソフトウェア開発をする全企業がターゲット
- 既存ツール（Dependabot, Snyk, Renovate）の検知は優秀だが、トリアージ＆修復が弱い → 明確な差別化ポイント
