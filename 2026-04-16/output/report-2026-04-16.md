# 新機能パッケージ製品アイデア レポート
日時: 2026-04-16。
ターゲットドメイン: セキュリティ監査。

## 選定アイデア: DepShield — 依存パッケージ脆弱性トリアージ＆修復PRサービス

### エレベーターピッチ
DepShield は、依存パッケージの脆弱性アラートを自動トリアージし、自社コードへの実際の影響度を評価した上で、テスト済みの修復 PR を生成する AI マネージドサービスです。

### なぜこのアイデアを選んだか（ハーネスの価値観点）
依存パッケージの脆弱性管理は、Dependabot のアラート数百件放置という業界共通の課題を抱えるコモディティ業務です。ハーネスの価値を最も明確に示せるドメインである理由は、AI が「影響なし」と判定したものの実は脆弱性が到達可能だった、というドリフト問題への対策が本質的に重要だからです。終了条件の外部管理（全 Critical/High にトリアージ結果付与済み、生成 PR のテスト全パス）を AI の自己申告ではなくハーネスでチェックする設計が自然にフィットします。さらに、PR 承認/却下の結果が明確なフィードバックシグナルとなり、ナレッジの自己改善ループが自然に回る点も、マネージドサービスとしての持続的価値を生みます。

### プロトタイプで実証できたこと
- ハーネスのライフサイクルフック（before/after scan, triage）が決定論的に AI の入出力を検証する仕組み
- 終了条件チェックリストによる AI 自己申告の排除（外部から 100%完了を確認）
- ドリフト対策: 低確信度（0.6）のトリアージ結果 3 件が自動的にヒューマンレビューにエスカレーション
- 品質チェック: reasoning 完全性、一貫性、Critical 偽陰性の 3 軸で自動検証
- ナレッジ改善ループ: 人間のフィードバック（medium→high 修正）からパターンを抽出し改善提案を生成

### プロトタイプの起動方法
```bash
cd 2026-04-16/prototype
npm install
npm run demo:mock
```

### 次のステップ（マネージドサービス化に向けて）
1. 実際の CVE/NVD データベースとのリアルタイム連携と、GitHub API を使った修復 PR 自動生成
2. マルチ言語対応（Python/Go/Rust 等のパッケージマネージャー対応）と CI/CD パイプライン統合
3. 複数顧客の匿名化フィードバックデータによるトリアージ精度の集合知改善

### 学んだこと / 気づき
- ハーネスの「サニティチェック」は、AI の出力を単にバリデーションするだけでなく、ビジネスロジック上の矛盾（Critical 脆弱性を影響なしと判定等）を検知する設計が重要
- 決定論的コード（到達の可能性分析）と AI 推論（コンテキスト依存のリスク評価）の境界設計が、サービスの信頼性と拡張性を決定する
- ナレッジ改善ループは「何を学ぶか」よりも「学んだことをいつ・どう反映するか」の承認フロー設計が難しい
- 厳格なリンター設定（max-statements: 10, no-magic-numbers 等）は、関数の責務分離を強制し、結果としてハーネス/エージェント/決定論的コードの三層分離と整合した
