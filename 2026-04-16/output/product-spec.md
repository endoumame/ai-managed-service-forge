# DepShield 設計書

## エレベーターピッチ
DepShield は、依存パッケージの脆弱性アラートを自動トリアージし、自社コードへの実際の影響度を評価した上で、テスト済みの修復 PR を生成する AI マネージドサービスです。

## ターゲットユーザー
- ペインポイント — Dependabot/Snyk が大量の脆弱性アラートを発行するが、トリアージに工数がかかり、数百件が未対応のまま放置される。「本当に危険なもの」がどれか判断するのに高度なセキュリティ知識が必要。
- 現在の解決方法 — シニアエンジニアが手動でトリアージ → 修復 PR 作成 → テスト確認。1 件あたり 30 分〜2 時間。または放置。
- 提供する価値 — 脆弱性アラートの自動トリアージ（到達の可能性分析付き）と、テスト済み修復 PR の自動生成。シニアエンジニアの判断を「承認/却下」のみに簡素化。

## システムアーキテクチャ

### ハーネス層
- ライフサイクルフック
  - `before:scan` — 対象リポジトリの lockfile とソースコードを取得・キャッシュ
  - `after:scan` — スキャン結果に対して到達の可能性分析を自動実行（決定論的コード）
  - `before:triage` — AI トリアージ前に、過去のトリアージ結果（ナレッジ）を注入
  - `after:triage` — AI のトリアージ結果をハーネスが検証（重大度 Critical なのに「影響なし」判定していないか等のサニティチェック）
  - `before:fix` — 修復 PR 生成前にテストスイートの現在の状態をスナップショット
  - `after:fix` — 生成された PR に対してテストスイート実行、カバレッジ比較
- 終了条件管理
  - [ ] 全対象パッケージのスキャンが完了
  - [ ] Critical/High 脆弱性の 100%にトリアージ結果が付与
  - [ ] Medium 以下の脆弱性の 80%以上にトリアージ結果が付与
  - [ ] トリアージで「要修復」と判定された項目に PR（または修復計画）が存在
  - [ ] 生成された全 PR のテストがパス
- 品質チェック機構
  - AI トリアージ結果の一貫性チェック（同じパッケージの同じ脆弱性に矛盾する判定がないか）
  - PR の diff サイズ閾値チェック（大きすぎる PR は分割提案）
  - テストカバレッジ低下検知（修復で既存テストが壊れていないか）
  - 偽陰性サニティチェック（Critical 脆弱性を「影響なし」としていないか）
- サブエージェント構成
  - Scanner Agent: 脆弱性データベース照合
  - Triage Agent: 影響度分析・優先度判定
  - Fix Agent: 修復コード生成・PR 作成

### AIエージェント層
- 担当タスク（推論アップサイドが大きい部分）
  - 脆弱性の自社コードベースへの影響度のコンテキスト判断（「この API エンドポイントは内部ネットワークのみでアクセスされるため、リモート攻撃のリスクは低い」等）
  - 破壊的変更を含むアップデート時のマイグレーションコード生成
  - トリアージレポートの自然言語生成（技術者以外のステークホルダー向け）
  - パッケージ間の依存関係の複雑な相互作用の分析
- 使用するツール/API
  - Claude API（claude-sonnet-4-20250514）: トリアージ推論、コード生成
  - GitHub API: PR 作成、ファイル読み取り
  - npm/yarn API: パッケージメタデータ取得
- ヒューマン・イン・ザ・ループのトリガー条件は以下のとおりである。
  - Critical 脆弱性のトリアージ結果は必ず人間承認
  - 破壊的変更を含む修復 PR は人間レビュー必須
  - 過去に「影響なし」判定が誤りだったパッケージの再トリアージ時
  - AI の確信度が閾値（70%）以下のトリアージ結果

### 決定論的コード層
- ルールベースで確実に実行する担当処理は以下のとおりである。
  - package.json / pnpm-lock.yaml / yarn.lock のパースと依存関係ツリー構築
  - CVE/NVD データベースとの照合（完全一致マッチング）
  - CVSS スコアに基づく重大度分類
  - SemVer 互換性チェック（メジャー/マイナー/パッチ判定）
  - 到達可能性の静的分析（import チェーンの追跡）
  - テスト実行とカバレッジ計算
  - Git 操作（ブランチ作成、コミット、PR 生成）
  - レポートのフォーマット変換（Markdown/JSON/HTML）

### ナレッジ自動改善ループ
1. **インプット（ユーザー行動/フィードバック）**:
   - PR 承認/却下のアクション
   - トリアージ結果の修正（「影響なし」→「要修復」への変更等）
   - マイグレーションコードの手動修正差分
2. **矛盾検知メカニズム**:
   - 同一パッケージ・同一脆弱性タイプに対する過去判定との矛盾チェック
   - 「影響なし」判定後にインシデントが発生した場合のアラート
   - ユーザーの修正頻度が高いパッケージの検知（AI 判断の精度が低い領域）
3. **承認フロー**:
   - ナレッジ改善提案をダッシュボードに表示
   - セキュリティ担当者が承認 → ナレッジベースに反映
   - 自動反映の閾値: 同一パターンの修正が 3 回以上蓄積した場合
4. **反映タイミング**:
   - 即座: 承認済みナレッジの新規スキャンへの適用
   - 日次: ナレッジ改善提案のバッチ生成
   - 週次: ナレッジベース全体の整合性チェック

## MVP（プロトタイプ）スコープ
実装する機能は以下の 3 つに絞ります。
1. 依存関係スキャン＆脆弱性照合 — package.json をパースし、モック脆弱性 DB と照合、到達の可能性を分析する
2. AI トリアージ＆レポート生成 — Claude API を使って脆弱性の影響度を判定し、トリアージレポートを生成（ハーネスによるサニティチェック付き）
3. ナレッジ自動改善提案 — トリアージ結果へのフィードバックを蓄積し、改善提案を生成

将来版で実装する機能は以下のとおりです。
- 実際の GitHub PR 生成（プロトタイプでは PR 内容のプレビューのみ）
- マルチ言語対応（Python/Go/Rust 等）
- 実際の CVE/NVD データベースとのリアルタイム連携
- CI/CD パイプライン統合
- Slack/Teams 通知
- ダッシュボード UI（CLI のみ）
