## アイデア 1: InvoiceForge — AI請求書処理パイプライン

### ユーザーが本当に欲しいもの（業務の完成品）
月末に届く数百枚の請求書が、正確な仕訳データとして会計システムに投入され、異常な請求だけが人間にエスカレーションされている状態。経理担当者は「確認・承認」だけに集中できる。

### ハーネス設計のキモ
- 「ライフサイクルフック」請求書取り込み → OCR/AI 抽出 → ルール検証 → 仕訳生成 → 人間承認の各ステップに before/after フック
- 「終了条件」全請求書に対して「抽出完了」「検証パス」「仕訳生成完了」「承認済み」の 4 フラグが立つこと
- 「品質チェック」抽出結果と元画像の突合チェック、金額合計の整合性検証

### AIが担う部分
- 請求書からの非構造化データ抽出（ベンダー名、金額、日付、品目）
- ベンダー名の名寄せ（表記ゆれ対応）
- 異常検知（通常と大きく異なる金額、新規ベンダー等）

### 決定論的コードが担う部分
- 消費税計算（税率判定・軽減税率対応）
- 仕訳ルールの適用（勘定科目マッピング）
- インボイス制度の適格請求書の要件チェック（登録番号検証）
- 承認ワークフロー制御（金額閾値による承認者決定）

### ナレッジ/データの自動改善ループ
- 人間が修正した抽出結果 → 次回以降の抽出精度向上
- 承認済み仕訳パターンの蓄積 → 自動仕訳の精度向上
- ベンダーマスタの自動更新 → 名寄せ辞書の充実

### 内製との差別化ポイント
- OCR モデルの継続的改善・最新モデルへの追従を自社でやるコストが不要
- インボイス制度の法改正対応をマネージドサービス側が吸収
- ベンダー名寄せ辞書は全顧客のデータで強化される（ネットワーク効果）

## アイデア 2: ExpenseGuard — 経費精算の自動監査サービス

### ユーザーが本当に欲しいもの（業務の完成品）
従業員の経費精算申請が、ポリシー違反・不正・入力ミスのチェックを完了した状態で経理部門に届き、明らかに問題ないものは自動承認、グレーゾーンだけが人間判断に回る状態。

### ハーネス設計のキモ
- 「ライフサイクルフック」申請受付 → レシート画像解析 → ポリシーチェック → 異常スコアリング → ルーティングの各段階にフック
- 「終了条件」全申請に対して「分類完了」「ポリシーチェック完了」「ルーティング完了」のフラグ
- 「品質チェック」レシート画像と申請内容の整合性、日付・金額の一致確認

### AIが担う部分
- レシート画像からの情報抽出
- 経費カテゴリの自動判定（あいまいなケースの推論）
- 不正パターンの検知（分割申請、架空経費等の異常検知）
- 自然言語での却下理由・指摘事項の生成

### 決定論的コードが担う部分
- 社内経費ポリシーとの照合（上限金額、対象カテゴリ、必要書類）
- 税務上の控除可否判定
- 承認フローの自動ルーティング
- 勘定科目の自動マッピング

### ナレッジ/データの自動改善ループ
- 承認者のジャッジ履歴 → ポリシー解釈の学習
- 不正として確定したケース → 不正検知モデルの強化
- 頻出する指摘事項 → 申請フォームのガイダンス改善提案

### 内製との差別化ポイント
- 経費ポリシーは会社ごとに異なるが、チェックロジックの骨格は共通
- 不正検知モデルは多社のデータで訓練されるほど精度が上がる
- 税制改正への追従コストをサービス側が負担

## アイデア 3: ReconcileBot — 銀行口座の自動消込サービス

### ユーザーが本当に欲しいもの（業務の完成品）
銀行口座の入出金明細と、社内の売掛金・買掛金台帳が自動的に突合され、マッチング済み・未マッチングのステータスが整理された状態。月次決算の消込作業が数時間から数分に短縮される。

### ハーネス設計のキモ
- 「ライフサイクルフック」明細取込 → 前処理 → 自動マッチング → 確信度分類 → 人間確認 → 消込確定
- 「終了条件」全明細に対して「マッチング試行完了」かつ「未マッチング分が人間にエスカレーション済み」
- 「品質チェック」消込後の残高突合、二重消込の検知

### AIが担う部分
- 振込名義と取引先名の名寄せ（表記ゆれ、略称対応）
- 複数明細の合算マッチング（分割入金の統合推論）
- 異常パターン検知（通常と異なる入金タイミング、金額）

### 決定論的コードが担う部分
- 金額完全一致による自動マッチング
- 日付範囲による候補絞り込み
- 残高計算と整合性検証
- 消込仕訳の自動生成

### ナレッジ/データの自動改善ループ
- 人間が手動マッチングした結果 → 名寄せ辞書の強化
- 分割入金パターンの学習 → 合算マッチング精度向上
- 取引先ごとの入金パターン学習 → 予測精度向上

### 内製との差別化ポイント
- 消込ロジックの開発は複雑だが、パターンは企業間で共通性が高い
- 銀行 API フォーマットの対応は開発・保守コストが大きい
- 名寄せ辞書は全顧客のデータで強化される

## アイデア 4: JournalCraft — AI仕訳起票アシスタント

### ユーザーが本当に欲しいもの（業務の完成品）
あらゆる取引（請求書、レシート、契約書、銀行明細）から、正確な仕訳データが自動的に起票され、経理担当者は例外ケースの判断と最終承認だけを行う状態。新人経理でもベテラン並みの仕訳精度を実現。

### ハーネス設計のキモ
- 「ライフサイクルフック」取引データ受信 → 文脈分析 → 仕訳候補の生成 → ルール検証 → 承認キュー投入
- 「終了条件」全取引に対して「仕訳候補の生成完了」「ルール検証パス」「承認待ちまたは承認済み」
- 「品質チェック」借方・貸方の合計一致、勘定科目の妥当性チェック、期間帰属の整合性

### AIが担う部分
- 取引内容の自然言語理解（摘要の解釈）
- 過去仕訳パターンとの類似度判定
- 新規取引パターンの勘定科目推論
- 仕訳の「なぜ」を説明する根拠生成

### 決定論的コードが担う部分
- 借方・貸方バランスの強制
- 勘定科目マスタとの照合
- 消費税区分の自動判定
- 部門・プロジェクトコードの自動付与ルール

### ナレッジ/データの自動改善ループ
- 承認済み仕訳 → 仕訳パターン DB の拡充
- 修正された仕訳 → AI の推論精度の改善
- 新規勘定科目の追加 → マッピングルールの自動更新提案

### 内製との差別化ポイント
- 仕訳ルールは業種・規模で異なるが、基本パターンの 80%は共通
- 税制改正時の勘定科目・税区分変更をサービス側が対応
- 複数顧客の仕訳パターンから業種別ベストプラクティスを提供

## アイデア 5: VendorSync — 取引先マスタ自動管理サービス

### ユーザーが本当に欲しいもの（業務の完成品）
取引先マスタが常に最新かつ正確で、新規取引先は請求書到着時に自動登録され、既存取引先の住所変更・社名変更・合併情報が自動反映される状態。インボイス制度の適格請求書の発行事業者の番号も自動検証・更新される。

### ハーネス設計のキモ
- 「ライフサイクルフック」新規検知 → 情報抽出 → 外部 DB 照合 → 名寄せ判定 → マスタ更新提案 → 承認
- 「終了条件」全新規候補に対して「既存マッチング試行完了」「外部 DB 照合完了」「承認待ちまたは反映済み」
- 「品質チェック」重複登録チェック、登録番号の国税庁 DB 照合、住所の正規化検証

### AIが担う部分
- 請求書・名刺・メールからの取引先の情報抽出
- 社名の表記ゆれ検知・名寄せ（「株式会社」「(株)」「㈱」の統一等）
- 合併・社名変更のニュース検知と関連付け

### 決定論的コードが担う部分
- 適格請求書の発行事業者の番号の国税庁 API 照合
- 住所の正規化（郵便番号 DB 照合）
- 重複候補のスコアリング（完全一致・部分一致の定量判定）
- マスタ更新のバージョン管理

### ナレッジ/データの自動改善ループ
- 名寄せの人間判断結果 → 名寄せルールの強化
- 社名変更パターンの蓄積 → 変更検知精度の向上
- 業界別の取引先ネットワーク情報 → 関連取引先の推薦

### 内製との差別化ポイント
- 外部 DB（国税庁、法人番号 DB 等）との連携保守コストが大きい
- 名寄せ精度は処理件数に比例して向上する
- 法改正（インボイス制度変更等）への追従をサービスが吸収
