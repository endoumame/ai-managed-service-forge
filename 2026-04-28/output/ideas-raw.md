# アイデア発散: 経理・請求書処理ドメイン

日時: 2026-04-28。

---

## アイデア 1: InvoiceForge — AI請求書仕訳オートパイロット

### ユーザーが本当に欲しいもの（業務の完成品）
請求書を受け取ったら、正しい勘定科目で仕訳が切られ、承認待ちキューに入り、期日管理まで完了している状態。経理担当者は「確認して承認ボタンを押すだけ」の状態になっていること。

### ハーネス設計のキモ
- Before-Tool フック — AI が勘定科目を推定する前に、仕入先マスタと過去仕訳履歴をコンテキストとして注入
- After-Tool フック — AI 推定結果を決定論的ルール（税率計算、貸借一致）でバリデーション
- 終了条件 —「請求書の情報抽出完了」「勘定科目の割当完了」「貸借一致確認」「承認ルーティング完了」の 4 チェックすべて通過
- 品質チェック — 金額の貸借一致を数式で検証（AI の自己申告を信じない）

### AIが担う部分（推論のアップサイドが大きく、ミスのダウンサイドが小さい部分）
- 請求書画像/PDF からの情報抽出（OCR + 構造理解）
- 過去の仕訳パターンから勘定科目を推定
- 請求書の異常検知（通常と異なる金額、新規取引先の検出）

### 決定論的コードが担う部分
- 消費税計算（税率 × 税抜金額の厳密計算）
- 貸借バランスの検証
- 支払期日の算出（契約条件マスタに基づく）
- 仕訳帳フォーマットへの変換

### ナレッジ/データの自動改善ループ
- ユーザーが勘定科目を修正 → 修正パターンを仕入先別に蓄積 → 次回から推定精度向上
- 新規取引先の初回処理結果 → マスタに自動登録提案
- 月次で「修正率」を集計し、修正率が高い仕入先のルールを再学習

### 内製との差別化ポイント
- AI モデルの進化に追従するコスト（プロンプト改善、新モデル対応）を顧客が負わない
- 複数顧客の匿名化された修正パターンから汎用的な改善を還元できる
- 会計基準の変更（インボイス制度対応等）をサービス側で一括対応

## アイデア 2: ExpenseGuard — 経費精算の不正・異常検知サービス

### ユーザーが本当に欲しいもの（業務の完成品）
月次で経費精算をレビューする際、不正の疑いがある申請や社内ポリシー違反がハイライトされ、根拠と共にレポートが出力されている状態。経理マネージャーは「フラグが立った案件だけ詳細確認する」ワークフローになること。

### ハーネス設計のキモ
- Before-Tool フック — 分析前に社内経費ポリシー（上限額、申請ルール等）をコンテキスト注入
- After-Tool フック — フラグ付けの根拠が具体的な数値・ルールに紐づいているか検証
- 終了条件 —「全申請スキャン完了」「フラグ件数確定」「レポート生成完了」
- 品質チェック — フラグなし判定の申請からランダムサンプリングで再チェック（見逃し防止）

### AIが担う部分
- 経費の異常パターン検知（通常と異なる使い方、時間帯の不自然さ）
- レシート画像と申請内容の整合性チェック
- 自然言語での異常についての理由説明と生成

### 決定論的コードが担う部分
- 経費上限超過の判定（金額比較）
- 申請期限チェック
- 重複申請の検出（完全一致・類似一致）
- レポートフォーマット生成

### ナレッジ/データの自動改善ループ
- 「フラグあり→調査→問題なし」のフィードバックで偽陽性を削減
- 新たな不正パターンが発覚 → 検知ルールに追加提案
- 部署別・カテゴリ別の統計で閾値を自動調整提案

### 内製との差別化ポイント
- 不正パターンのナレッジは業界横断で蓄積可能（自社だけでは事例が少ない）
- ポリシー変更時の検知ロジック更新を自動化
- 監査法人への説明資料としてそのまま使えるレポート品質

## アイデア 3: PayFlow — 支払サイクル最適化 & キャッシュフロー予測

### ユーザーが本当に欲しいもの（業務の完成品）
今月の支払スケジュールが最適化され、キャッシュフローへの影響が可視化された状態。「いつ何を支払うべきか」が優先度付きで提示され、早期支払割引の機会も自動で検知されていること。

### ハーネス設計のキモ
- Before-Tool フック — 銀行残高情報と支払予定一覧を注入
- After-Tool フック — 提案された支払スケジュールが残高を下回らないか検証
- 終了条件 —「全請求書の支払日決定」「残高シミュレーション完了」「レポート出力完了」
- 品質チェック — 支払日が契約上の期限を超過していないか決定論的に検証

### AIが担う部分
- 取引先との関係性を考慮した支払優先度の推定
- キャッシュフロー予測のシナリオ分析（楽観・悲観・中間）
- 早期支払割引の適用判断（割引率 vs 資金コストの比較分析）

### 決定論的コードが担う部分
- 日次残高シミュレーション計算
- 支払期限のカレンダー計算
- 割引金額の正確な計算
- 銀行振込データ（全銀フォーマット等）の生成

### ナレッジ/データの自動改善ループ
- 実績キャッシュフローと予測の差分を蓄積 → 予測精度向上
- 取引先の支払条件変更を自動検知 → マスタ更新提案
- 季節変動パターンの学習

### 内製との差別化ポイント
- 業界平均の支払サイクルベンチマークを提供（自社単独では不可能）
- 銀行 API 連携やフォーマット対応の保守コストをサービスが吸収
- 資金繰りのベストプラクティスが自動的に反映

## アイデア 4: ReconcileBot — 自動消込・突合マネージドサービス

### ユーザーが本当に欲しいもの（業務の完成品）
銀行の入出金明細と請求書・売掛金/買掛金が自動で突合され、消込済み・未消込・不一致がダッシュボードで一目瞭然の状態。月次決算の消込作業が「不一致案件の判断」だけに短縮されていること。

### ハーネス設計のキモ
- Before-Tool フック — 消込ルール（完全一致、金額許容差、分割消込ルール等）をコンテキスト注入
- After-Tool フック — 消込提案の整合性検証（同一入金を二重消込していないか等）
- 終了条件 —「全入出金明細に対する消込の候補提示が完了」「未消込の件数が確定」「不一致レポート完了」
- 品質チェック — 消込後の残高と帳簿残高の一致を算術的に検証
- サブエージェント — 大量明細を並列処理するためのバッチ分割管理

### AIが担う部分
- 摘要文（振込人名の表記揺れ）のマッチング
- 分割支払い・まとめ支払いのパターン推定
- 不一致原因の推定と対応策提案

### 決定論的コードが担う部分
- 金額完全一致による自動消込
- 許容差内の金額マッチング
- 消込後残高の計算
- 二重消込防止チェック

### ナレッジ/データの自動改善ループ
- ユーザーが手動消込した表記揺れパターンを蓄積 → 次回から自動マッチ
- 分割支払パターンを取引先別に学習
- 月次で「手動消込率」を KPI として追跡、低下傾向なら改善提案

### 内製との差別化ポイント
- 銀行フォーマットの多様性（全銀、各行独自 CSV 等）への対応保守
- 表記揺れパターンは顧客横断で蓄積可能（「カ）」「(株)」「株式会社」等）
- 消込ロジックのエッジケース対応が継続的に改善される

## アイデア 5: InvoiceAudit — 請求書受領から監査証跡までのE2E管理

### ユーザーが本当に欲しいもの（業務の完成品）
受領した請求書が電子帳簿の保存法に準拠した形で保管され、検索可能なインデックスが付与され、監査時にすぐ提出できる状態。インボイス制度対応（適格請求書の要件チェック）も自動化されていること。

### ハーネス設計のキモ
- Before-Tool フック — 電子帳簿の保存法の要件チェックリストと適格な請求書の発行事業者の番号の検証 API 情報を注入
- After-Tool フック — 保存要件（タイムスタンプ、検索要件 3 項目）を満たしているか決定論的に検証
- 終了条件 —「情報抽出完了」「要件チェック完了」「インデックス登録完了」「保存完了」
- 品質チェック — 国税庁の適格な請求書の発行事業者の公表サイトとの突合（登録番号の実在確認）

### AIが担う部分
- 請求書からの情報抽出（発行者、金額、日付、登録番号等）
- 請求書の種類判別（適格請求書/簡易な適格請求書/非適格）
- 不備箇所の自然言語での指摘と修正依頼文案の生成

### 決定論的コードが担う部分
- 登録番号のフォーマット検証（T + 13 桁数字）
- 電帳法の保存要件チェック（日付・金額・取引先での検索可否）
- タイムスタンプの付与
- 保存期間管理（7 年/10 年の自動計算）

### ナレッジ/データの自動改善ループ
- 不備が多い取引先を記録 → 受領時に重点チェック
- 法改正情報を定期取得 → チェックルールの更新提案
- 過去の監査指摘事項をパターン化 → 事前防止

### 内製との差別化ポイント
- 法改正対応の保守コストをサービスが吸収（インボイス制度、電帳法の改正は頻繁）
- 監査法人・税務調査で求められるフォーマットへの対応
- 適格な請求書の発行事業者の番号の有効性チェック API 連携の保守
